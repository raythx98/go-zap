# Decisions

Architecture decision records — why things are the way they are.

---

## ADR-001: Layered architecture (controller → service → repository)

**Decision**: The codebase follows a strict three-layer architecture: controller (HTTP), service (business logic), repository (data access).

**Rationale**: Clear separation of concerns. Controllers don't know about SQL; services don't know about HTTP. Each layer is independently testable. Services are tested with mock repositories; no HTTP harness needed.

**Tradeoff**: More files and indirection than a flat handler approach. Justified by testability and maintainability.

---

## ADR-002: Interface-based dependency injection

**Decision**: All major components (services, repositories) define interfaces. Dependencies are injected via constructor functions in `resources/`.

**Rationale**: Enables unit testing with mockery-generated mocks. No global state. Composition root in `resources/` makes wiring explicit and auditable.

---

## ADR-003: SQLC for database access

**Decision**: All database queries use SQLC-generated functions rather than an ORM.

**Rationale**: Type-safe SQL at compile time. No hidden queries or N+1 risks. SQL is explicit and reviewable in `sqlc/query.sql`. Consistent with the approach used in go-dutch.

---

## ADR-004: Basic Auth for API access control

**Decision**: Registration, login, and redirect tracking endpoints are protected by HTTP Basic Auth (in addition to JWT for authenticated endpoints).

**Rationale**: Prevents anonymous creation of accounts and anonymous redirect tracking. The Zap frontend is the only intended consumer — Basic Auth credentials are shared with it via environment variables.

**Tradeoff**: The Basic Auth password must be rotated via environment variables and CI secrets. Not suitable for multi-tenant or public API scenarios.

---

## ADR-005: Soft deletes for URLs

**Decision**: Deleted URLs set `is_deleted = true` rather than removing the row.

**Rationale**: Allows short URL reuse after deletion (the partial unique index on `short_url WHERE is_deleted = false` allows a new entry with the same short URL). Preserves redirect history for analytics.

**Tradeoff**: All queries must filter `WHERE is_deleted = false`. SQLC functions handle this consistently.

---

## ADR-006: Swagger documentation via code annotations

**Decision**: API documentation is generated by `swag` from annotations in controller and DTO files rather than maintaining a separate OpenAPI spec.

**Rationale**: Keeps documentation co-located with the implementation. Running `make swagger` regenerates the spec from source. Less risk of documentation drift.

**Tradeoff**: Swagger annotations add verbosity to DTO and controller files.

---

## ADR-007: `gohelpme` for shared middleware and utilities

**Decision**: Middleware (logging, auth, rate limiting, CORS, error handling) comes from `github.com/raythx98/gohelpme` rather than being reimplemented per-service.

**Rationale**: Consistent behavior across go-dutch and go-zap. Shared library means fixes and improvements apply to both services simultaneously.

**Tradeoff**: Tied to the gohelpme version pinned in `go.mod`. API changes in gohelpme require coordinated updates in consumers.

---

## ADR-008: Single OCI instance deployment

**Decision**: The entire stack (Caddy, app, database) runs on one Oracle Cloud instance via Docker Compose.

**Rationale**: This is a personal project. The cost and operational overhead of Kubernetes or managed database services is not justified. Podman is used instead of Docker (daemonless, rootless).

**Tradeoff**: Single point of failure. No horizontal scaling. Acceptable for personal use.
